## 스키마
| 컬럼 | 설명 |
|------|------|
| date | YYYY-MM-DD (월간은 월초) |
| regime | 물가 / 금리 / 부동산 / 가계대출 / 대외통상 / AI반도체 / 증시실적 |
| group | 대분류 파일은 regime과 같고, 세부 파일은 세부 그룹명 |
| keywords | 그룹에 묶인 검색어 (`\|` 구분) |
| score | 데이터랩 원값. **같은 요청 안에서만** 상대비교 |
| anchor_score | 같은 요청에 함께 보낸 앵커 그룹(`은행`)의 값 |
| score_rel | `score / anchor_score`. **이 값을 분석에 쓴다** |
| period_start / period_end | 조회 구간 (고정) |
| collected_at | API 호출 시각 (ISO 8601, Asia/Seoul) |

## score_rel을 쓰는 이유

데이터랩 지수는 요청에 포함된 그룹·기간 전체에서 검색량이 가장 큰 지점을 100으로 두는
상대값이다. 두 가지 문제가 따라온다.

1. **한 요청에 큰 그룹과 작은 그룹을 섞으면 작은 쪽이 눌린다.** 직전 버전은 대분류마다
   세부 5그룹을 한 요청에 보냈는데, `원자재유가`가 100을 가져가는 바람에 `근원물가`의
   최댓값이 0.09까지 눌려 유효숫자가 두 자리밖에 남지 않았다.
2. **요청이 다르면 100의 기준도 달라 서로 비교할 수 없다.**

그래서 지금은 **요청 1건에 대상 그룹 1개 + 앵커 그룹 1개**만 보낸다. 대상 그룹의 피크가
100이 되어 해상도를 다 쓰고(현재 28개 세부 그룹 중 25개가 100에 도달), 같은 요청 안의
두 그룹 비율은 실제 검색량 비율이므로 `score / anchor_score`가 요청을 가로질러
비교 가능한 값이 된다.

앵커는 `은행` 한 단어다. 후보 8개 중 월별 변동계수가 0.185로 가장 낮았다
(경제 0.307, 주식 0.640). 재확인: `python -m api.collect_datalab --calibrate`

## 조회 구간 고정

`config.yaml`의 `data_buffer_start` ~ `study_period_end`(2016-01-01 ~ 2026-07-31)를 쓴다.
지수가 구간 상대값이라 종료일이 하루만 바뀌어도 전 구간 숫자가 달라진다.
직전 버전은 종료일을 수집 당일로 잡아 재실행할 때마다 결과가 달라졌다.
